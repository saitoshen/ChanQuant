## P0 · 多品种「理论 vs 实际」对不上：工作区成员资金合计 720 万，总资金只有 100 万

### 先纠正上一版的一处错算（10:45）

上一版写「SN 一手保证金 48.1 万、27 个品种保底 1 手要 151.3 万」——**错了，差 10 倍**。

`symbols.json` 里根本没有 `mult` 字段（只有 margin / fee），我当时用了兜底值 10。
真实乘数在 `symbols_info` 表里：SN = **1**。所以

```
SN 一手保证金 = 349,020 元/吨 × 1 × 13.78% = 48,095 元 ≈ 4.8 万
```

27 个品种各 1 手合计 **96.5 万**（不是 151.3 万）。同理 PT 是 5.7 万不是 572 元、IC 14.9 万、
AU 13.6 万。**单价、乘数、保证金率三者相乘之后才是占用，任何一项取兜底值都会错一个数量级。**

### 实测数据（2026-11-19 10:45，`symbols_info` + 各品种最新收盘价）

| 项 | 数值 |
|---|---|
| 工作区「短线策略」总资金 | **100 万** |
| 7 个成员分配合计 | **720 万**（6 条各 30 万 + 多品种 **540 万**） |
| 多品种（`sid=67c189ab5471`，27 品种） | 540 万 ÷ 27 = **每品种 20 万** |
| 27 个品种按 20 万算出的保证金合计 | **5,188,010 元 = 540 万的 96.1%** |

各品种 1 手保证金（元）与 20 万预算下的手数：

|---|---|---|---|---|---|
| AU 黄金 | 135,911 | 1 | RB 螺纹 | 2,073 | 97 |

**关键结论：在 540 万 / 27 品种下，实盘与回测逐品种手数完全一致**（两边合计都是 5,188,010）。
所以「两边口径不一致」这件事，10:40 那次统一之后已经不存在了，`_size` 的保底 1 手也没有
被触发过（最便宜的 IC/IM 也是 1.35 手 > 0.5）。

### 真正的原因：配置层的钱对不上，不是公式

```
工作区总资金 100 万   ←  成员分配合计 720 万   （差 620 万，多品种一条就是总资金的 5.4 倍）
```

引擎按 540 万给 27 个品种各分 20 万，**它并不知道这个工作区只有 100 万**。
真到下单时，账户（091438 · SimNow）扛不住 518.8 万保证金，只能先到先得：

| 证据 | 内容 |
|---|---|
| `live_positions.json` 10:47 | 这条 27 品种策略**只有一条腿有仓**：`67c189ab5471#LH_DCE` → `DCE.lh2701: -17` |
| `trade_limits.json` 10:47 | 091438 今日 `orders=11 / cancels=7` |
| 其余 26 个品种 | 账本里没有记录 = 从未成交 |

17 手 LH 恰好对应「`DCE.lh2701` 一手 12,180 × 17 ≈ 20.7 万」，和「每品种 20 万」对得上 ——
**这反过来证明工作区分到它头上的确实是 540 万**，只是账户里没有这么多钱。

### 修法

**A. 配置先对齐（不用改代码，今天就能做）**
成员分配合计必须 ≤ 工作区总资金。当前 6 条单品种各 30 万（180 万）+ 多品种 540 万 = 720 万，
而总资金只有 100 万。两种选择：

- 总资金提到 **≥ 720 万**，多品种保持 540 万（每品种 20 万，27 个品种都参与）；
- 或者总资金保持 100 万，把多品种降到 100 万 - 其他成员占用的剩余 —— 此时每品种只有
  `剩余 ÷ 27`，贵的品种（AU/IC/IM/SC/PT/CU/SN）会明显被压缩。

**B. 界面必须把这个矛盾显示出来（防复发，这是核心）**
组合页/工作区页显示一行：`成员合计 720 万 / 总资金 100 万 · 超出 620 万`，超了标红。
现在界面上完全看不出来 —— 每个策略单看都「资金 100%」，加起来是总资金的 7 倍。

**C. 现金缓冲：96.1% 的保证金占用是危险配置**
即使钱对上了，27 个品种满打满算吃掉 96.1% 权益，手续费 + 盘中波动一起来就会被动强平。
建议 `capital_pct` 配到 70–80%（每品种 20 万 × 75% = 15 万），把缓冲留出来。

**D. 「预算不足半手就不开」（保留，但已不是主因）**
`_size()` 给子槽位加 `allow_zero`：`raw < 0.5` 时返回 0。单品种策略仍保底 1 手。
只有在「工作区钱很少、品种很多」时才会用到，现在这套配置下不会触发。

### 验收

- [ ] 工作区页显示「成员合计 / 总资金」，超出时标红；
- [ ] 成员合计 ≤ 总资金，不再出现 720 万配 100 万；
- [ ] 540 万 + `capital_pct=75%`：27 个品种逐品种手数 = 回测手数（selftest 已有口径锁）；
- [ ] 27 个品种占用合计 ≤ 权益 80%，留出缓冲；
- [ ] 单品种策略仍最少 1 手（不因这次改动变 0 手）。

## P1 · 台账闸门重构：`based` → `reconciled`（只减不增）

### 为什么

「加载时不按台账自动交易」（11-17 的要求）本身是对的，但实现用了 `based` / `based_target`
这套「目标变过没变」的时间维度判据去回答「账本可不可信」这个数据维度的问题。
后果：25 处引用、3 个地方手动维护同一个布尔位（`_rebalance` 首次、`delta==0`、`_sync_after_align`），
并且已经长出两个例外（减仓、纯建仓），还在继续长。

### 目标

一条规则替代整套闸门：**账本与账户没对上时，只减不增。**

```python
def _attrib(self, st, sym):
    """账户里能算到本策略头上的净仓。None = 持仓还没就绪。"""
    if self._pos is None:
        return None
    return self._net_pos(sym) - self._others_book(st, sym)

attrib = self._attrib(st, st.underlying)
if attrib is None:
    return
st.reconciled = (attrib == held)
if not st.reconciled:
    if not (held and abs(int(st.target)) < abs(held)):
        st.last_action = "账本与账户还没对上（只减不增），可点一键对齐"
        return
```

`_others_book()` 已存在（本次为修「纯建仓被挡」新增），直接复用。

### 步骤

1. [ ] 加 `SlotState.reconciled: bool = False`，`_attrib()` 落地；
2. [ ] 让它与现有 `based` 判据**并存**跑一天，日志里两条结论不一致时报错（暴露两者分歧的场景）；
3. [ ] 确认无分歧后，删掉 `based` / `based_target` 全部 11 处（`strategy_runner.py`）与 `_sync_after_align` 里的手工重置；
4. [ ] 重写 `selftest.py` 里 14 处相关断言，改成 reduce-only 口径：
   - 账本与账户不一致 + 减仓 → 发
   - 账本与账户不一致 + 加仓/建仓 → 不发
   - 账本与账户一致 → 完全按 target−held 走（不再有任何闸门）
   - `_pos is None` → 不发
5. [ ] 收盘后改，次日开盘验证；改错代价是重复开仓，绝不能在盘中动。

### 风险

`_net_pos` 依赖持仓推送的实时性。刚成交那一刻账户还没跟上，会短暂判成「不一致」→ 退化成只减不增。
这和现在的 `_side_pos` 判据同源，行为一致，不会更差；但要在日志里保留一行，方便事后确认。
